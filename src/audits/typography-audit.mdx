## 1. Why this exists

The dashboard's text has grown screen by screen with no shared rules: **93 different text styles** where a design system needs **10**.

<div style={{ display: "flex", flexWrap: "wrap", gap: 12, margin: "18px 0" }}>
  <Stat value="93" label="Text styles found" tone="#B42318" />
  <Stat value="10" label="Text styles proposed" tone="#1F7F80" />
  <Stat value="2,885" label="Text elements measured" />
  <Stat value="22" label="Pages audited" />

This matters for three reasons:

- **Brand and polish.** Every native button renders in **Arial** instead of our brand font, and the page title comes in three different sizes depending on the page. Users read this as "something feels slightly off" even if they can't say what.
- **Speed.** Without a shared scale, every new screen re-decides basic type choices. Controls (buttons, dropdowns, inputs, form labels) account for a third of all the variations. That is where design and engineering time leaks and where QA keeps finding small inconsistencies.
- **Accessibility and accuracy.** Our pink and teal link text fails WCAG AA contrast. The "light" font weights in our CSS and designs aren't in our font kit, so what we design isn't what ships.

**Proposal:** adopt one type system (1 font, 3 weights, 10 named styles, plus rules) as the foundation of the Nimbus design system, documented in Storybook. New work uses it by default, and existing pages migrate gradually, starting with buttons and form controls, where the gain is biggest. Several fixes are one-line CSS changes.

**Ask:** agreement to adopt it as the standard, plus a small amount of engineering time for the quick wins and the control migration.

**How it was measured**

- Every visible element with its own text, plus inputs and selects, was read from the browser's computed style: font family, size, weight, line-height, letter-spacing, text-transform and color.
- Styles were grouped by those properties. Each group is one "style" in this report.
- First pass: desktop width, sidebar expanded, Nimbus Exchange / Tango account context. A second pass mapped every style to the pages it appears on (the links throughout this report) and pulled the HTML and matching CSS rules quoted in the findings.

**Not covered**

- The documentation site (`/docs/`), which the browser tool couldn't read.
- Modals, hover and focus states, error messages and open dropdown menus.
- n+ payee registration, n+ payment history and n+ invoice history beyond the title and access-denied message (the audit account lacks permission there).
- Browser-extension overlays, which aren't part of the app.

**Also observed in the second pass (not counted in the 93)**

- About 9 extra styles appeared on Realtime dashboard, Buyer breakdown and Benchmarks once more live data loaded (for example 13px/700 text in #999999 and #7BCACD, and an 11px/300 uppercase label with 0.4px tracking). The real total is therefore slightly higher than 93.
- Some sizes shift with window width: body text measured 16px at one width and 15px at another, and the base line-height moved between 36px and 33.75px. The type scale isn't fixed across breakpoints.

## 4. Analysis: where the inconsistency comes from

**The problem is concentrated.** Five styles cover 67% of all text: table cells (912 uses, 32%), sidebar links (528, 18%), admin bar links (198, 7%), sidebar section headers (154, 5%) and table headers (136, 5%). The other **88 styles cover the remaining third**, and 52 of them appear on only one page. Fixing the shared components (table, sidebar, buttons) fixes most of what users see. The long tail is one-off page CSS.

**Five root causes, seen directly in the CSS:**

1. **No type tokens.** Sizes, weights and colors are hard-coded per selector, often several levels deep, e.g. `.activity-container .page-header-menu .grid-auto-auto .nav-item-wrapper …` sets its own 13px/20px olive text. Every new screen adds another variation.
2. **Base element styles that are always overridden.** `h2, h3, h4 { font-weight: 600 }` and `h6 { font-weight: 500 }` are never what renders, because `.bold` or `.extra-bold` always overrides them. `label { 12px; 700; uppercase }` is overridden into a 26px number (`.value-label`) and a 13px/600 capitalized checkbox label (`.checkbox-container`). Base styles carry no meaning, so each use re-styles from scratch.
3. **Native element defaults leaking through.** The global button rule sets size, weight, tracking and case but no `font-family`, so every `<button>` falls back to Arial. Inputs are sized in points (`13pt`) with em line-heights (`2.25em`, `2.8em`), which produces 17.33px text on 39–48.5px lines.
4. **Line-height used for layout.** Row and control heights are set with line-height (`line-height: 62px` on a report dropdown, 59px on tabs, 36px inherited by table text). This creates most of the "same font, different line-height" variations.
5. **Font kit and third-party mismatches.** The Typekit kit has no proxima-nova 200 or 300, but the CSS asks for both. The charting library uses its own default font (Lucida Grande) for one axis.

<Finding n={1} title="Every native button renders in Arial" level="High">

Native `<button>` elements don't inherit the page font, and the global button rule never sets `font-family`. As a result, 9 distinct button styles compute to Arial. Buttons built as links (`<a class="button">`) render in proxima-nova, so the typeface depends on which tag a developer used.

**Where to see it**

- "Save Query" / "Collapse": 13px/800 Arial on [Performance insights](https://dashboard-stage.adsbynimbus.com/#/performance-insights), [Buyer breakdown](https://dashboard-stage.adsbynimbus.com/#/buyer-breakdown), [Manage active demand](https://dashboard-stage.adsbynimbus.com/#/demand/timehop), [Manage active n+ demand](https://dashboard-stage.adsbynimbus.com/#/nimbus-plus-demand/timehop) +5 more
- "CHANGE" / "UNPUBLISH" row buttons: 11px/800 Arial on [Manage active demand](https://dashboard-stage.adsbynimbus.com/#/demand/timehop), [Manage active n+ demand](https://dashboard-stage.adsbynimbus.com/#/nimbus-plus-demand/timehop), [n+ payments](https://dashboard-stage.adsbynimbus.com/#/payments-overview), [Manage campaigns](https://dashboard-stage.adsbynimbus.com/#/deal-activation-setup/manage) +1 more
- "LOAD ALL" / "UNBLOCK": 12px/800 Arial on [Ad blocking](https://dashboard-stage.adsbynimbus.com/#/blocking)

## 8. The finalized type system

One set is enough: usage clusters cleanly into one scale, so the "up to three type sets" fallback isn't needed.

- **Family:** proxima-nova (Adobe Fonts), fallback `"Helvetica Neue", Helvetica, Arial, sans-serif`
- **Weights:** 400 Regular · 700 Bold · 800 Extra Bold

## 9. Rules

**Family and weight**

- One family: proxima-nova. Retire proxima-nova-condensed and the Lucida Grande and Arial fallbacks.
- Three weights only: 400 for reading text; 700 for headings, labels, emphasis and links; 800 for uppercase interactive text.
- Never specify 200, 300, 500 or 600. 200 and 300 aren't in the font kit; 500 and 600 are too close to their neighbors to read as a distinct level.
- Weight is the only per-instance modifier: body-lg, body and caption may go to 700 (`.type-strong`).

**Size and spacing**

- Only scale sizes: 40, 28, 20, 16, 14, 12, 11 px. No points, no in-between pixels.
- Line-height belongs to the token. Row, tab and input heights come from padding or min-height, never line-height.
- 14px body is the default. Use 16 for things people type or select, 12 for supporting text.
- Use tabular figures for KPIs, tables, dates and anything that aligns in columns.

**Case and tracking**

- Uppercase only for label, button and badge, always with +0.06em tracking.
- Never uppercase body text, values or numbers.
- Negative tracking (−0.01em) only on display and headline. Everything else is 0.
- Sentence case for titles and table headers ("Demand source", not "Demand Source").

**Hierarchy and semantics**

- Every page has exactly one `type-headline` as `<h1>`, including access-denied pages.
- Tag follows token: h1 = headline, h2 = title, h3 = subtitle. Don't skip levels.
- At most three type levels inside one card: subtitle, body, caption/label.
- Pink (action) means clickable. Teal means selected or positive. Don't use either for static text.
- `<label>` is only for form fields; `<button>` and link-buttons look identical.

## 12. Open decisions

These defaults are applied above. Confirm or change them before the Storybook page is final.

1. **Body default 14px vs 15px.** Today's paragraphs and sidebar are 15px and tables are 14px. The scale picks 14px for density. 15px would add an eighth size.
2. **Darker pink and teal for text.** These are needed for WCAG AA. Brand fills don't change.
3. **Sentence case** for titles and table headers (today it's mostly Title Case).
4. **Sidebar section headers:** body-strong (closest to today's look) or `type-label` uppercase.
5. **Page title = publisher name.** Should the h1 stay the publisher name (Tango) or become the page name (Manage active demand), with the publisher shown in the switcher?
